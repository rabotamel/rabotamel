# Заметки для разработки (читать перед правками сообщений бота)

## Рандомизация сообщений бота — ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ПРОЕКТА

В проекте есть структура рандомизации сообщений: у каждого бота свой, один раз подобранный и затем неизменный
вариант текста — случайные синонимы, близкие по смыслу эмодзи, несколько вариантов компоновки.

**Сейчас рандомизированы:** капча (`app/captcha.py`), приветствие (`app/greeting.py`) inline-кнопки «Магазин» / «Галерея»
под приветствием (`app/shop_buttons.py`), раздел «Галерея» (`app/gallery.py`), общий декоративный маркер (`app/deco.py`)
и «Предложка» — подпись кнопки в галерее и текст меню предложки (`app/suggest_ui.py`).

**В будущем это будет добавляться к другим сообщениям бота.** Если владелец проекта просит для нового сообщения
«рандомизацию», «как у приветствия/капчи», «подбор синонимов и смайликов» — делайте по схеме ниже, не изобретая
новую. Если он просит новое сообщение бота без таких оговорок — спросите, нужна ли рандомизация.

### Правила (общие для всех сообщений)
1. Вариант создаётся **один раз при создании бота** (при первом запуске) детерминированно по seed = токен бота
   и хранится в БД. Перезапуски, обновления кода, повторные `/start` его не меняют.
2. Хранить нужно **готовый результат** (для текста — шаблон с плейсхолдерами вроде `{name}`, `{balance}`),
   а не только индексы: правки словарей в коде не должны менять тексты уже работающих ботов.
3. Новый вариант у разных ботов не должен совпадать (`signature()` + набор `taken`).
4. Единственный способ сменить вариант у живого бота — функция «Уникальные текста» (кнопка «Перенаписать текста»)
   во вкладке «Песочница» (меняет сразу все виды сообщений, применяется без перезапуска бота, с переспросом).
   Интерфейс не расписывает, что именно рандомизируется, — только заголовок, описание и кнопка.
5. Смысл не меняется: синонимы равнозначны, тон нейтральный и спокойный (без фамильярности).
6. Эмодзи подбираются наборами (палитрами), которые сочетаются по стилю. Нельзя менять 🍬 — это валюта бота.
7. Никаких декоративных разделителей (`———`, `---`, `***`) и псевдографических рамок.
8. Индексы в словарях синонимов/эмодзи только **добавляются в конец**, не переставляются и не удаляются.
10. Цитата в приветствии (вариант `quote_points`) всегда отделена пустой строкой от заголовка и от баланса. Уже сохранённые
   в БД шаблоны без отступов исправляются при чтении (`greeting._space_quote`), перезаписывать их не нужно.
9. Владелец убрал из приветствия вариант «баланс в цитате» (`quote_balance`) — выглядит криво. Баланс не оформляется
   цитатой ни в каком варианте. У ботов, у которых такой шаблон уже сохранён, он остаётся до «Перенаписать текста».

### Как добавить новое рандомизируемое сообщение
1. Создать модуль `app/<имя>.py` по образцу `app/greeting.py`: словари синонимов и эмодзи, `generate_config(seed, taken)`,
   конфиг-класс с `to_json()`, `from_json()`, `signature()`, функция `render(...)`.
2. Зарегистрировать в `app/texts.py`: добавить `TextKind(...)` в `KINDS` и свойство в `BotTexts`.
   Хранение отдельной колонки не требует: всё новое лежит в `bot_profiles.texts_config` (JSON `{вид: JSON-конфиг}`).
   (Капча исторически лежит в `bot_profiles.captcha_config` — `LEGACY_COLUMNS`.)
3. Больше ничего подключать не надо: `repo.get_or_create_texts` создаст вариант при запуске бота, а кнопка в «Песочнице»
   перерандомизирует его вместе с остальными. Отправку сообщения в `handlers.py` делать через `texts.<вид>`
   (читать в момент отправки, не кэшировать), чтобы перерандомизация действовала без перезапуска.
4. Добавить пример и проверки в `tests/` (детерминированность, сохранение 🍬, отсутствие разделителей).
5. Если у сообщения есть динамические значения (имя, число) — подставлять их в момент отправки, экранируя HTML.

## Картинка в сообщениях бота
У бота есть необязательная ссылка на картинку (`bot_profiles.message_image_url`, поле в настройках бота; в идеале
1680 × 940). Она показывается над текстом во ВСЕХ сообщениях бота, кроме капчи, — одним сообщением (фото с подписью).
Любое новое сообщение пользователю отправляйте через `messaging.send_message(bot, chat_id, html_text, profile.message_image_url)`,
а не через `bot.send_message`; капча остаётся без картинки, как и короткие уведомления (см. «Картинка в уведомлениях» ниже). Служебное сообщение админу при запуске (`manager._greet`) — не в счёт.

Картинку сервер сначала скачивает сам (`avatars._download` — только публичные адреса, редиректы, до 5 МБ), приводит к JPEG
(стороны до 2560 px) и загружает в Telegram файлом; если скачать не вышло, Telegram получает саму ссылку. Так работает с
любыми хостингами картинок. После первой отправки запоминается `file_id`. Причина неудачи пишется в лог (`bot.messaging`).

## Числа в сообщениях
Числа для пользователей и в панели пишутся БЕЗ разделителей разрядов: `1000`, а не `1 000` (`greeting.format_number`,
`currency.format_money`, `fmtNum`/`fmtMoney` в `app.html`). Дробная часть — через запятую: `1234,5`.

## Капча: какой фрукт выбирать
Содержимое капчи (формулировка + 4 фрукта) привязано к рандомайзеру и хранится в БД, а вот КАКОЙ из 4 фруктов надо выбрать —
меняется при каждом показе (каждый `/start`) и не зависит от «Перенаписать текста». Состояния по пользователю нет: в кнопках
лежит случайный nonce (`cap:<фрукт>:<nonce>`), целевой фрукт = HMAC(токен бота, user_id + nonce) (`captcha.target_for`).
Новый показ даёт фрукт, отличный от прошлого; после неверного ответа задание остаётся тем же, меняется порядок кнопок.
Старые сообщения с капчей без nonce проверяются по `target` из конфигурации (поле оставлено для совместимости).

## Боты без токена (шаблоны в очереди)
`bot_profiles.token` может быть NULL: бот добавлен «заранее» без токена. Такой бот стоит в очереди (`status = queued`,
участвует в порядке и перетаскивании), но: `repo.claim_next` и `repo.has_spare` его пропускают, `repo.activate` и
`POST /api/bots/{id}/activate` отказывают, `/api/bots/{id}/token` отдаёт 404, рандомизируемые тексты для него не создаются
(они создаются по токену при первом запуске). В панели — красная пометка (`has_token: false` в `_bot_dict`). Токен добавляется
один раз через «редактировать» (`repo.set_token`, только пока токена нет; проверяется формат, уникальность и Telegram).
Миграция: `ALTER TABLE bot_profiles ALTER COLUMN token DROP NOT NULL` (в `db.init_db`). Новый код, который берёт `bot.token`,
обязан учитывать, что у бота из очереди он может быть None.

## Повторный /start
Приветствие, присланное после `/start` или после прохождения капчи, запоминается (`last_greeting` в `handlers.py`, в памяти).
При следующем `/start` прежнее приветствие удаляется; капча при повторном `/start` тоже заменяется новой.

## Пользователи и конфеты
- Пользователь считается «новым» и попадает в БД **только после успешной капчи** (`UserStats.add` вызывается лишь из
  обработчика верного ответа). Не прошедшие капчу не пишутся в БД вообще.
- Проверка «прошёл ли капчу» — по словарю в памяти (`UserStats`), записи в БД копятся и уходят одной транзакцией
  на пачку (`flush`, раз в 15 с и сразу после прохождения капчи). Юзернейм пользователя хранится в `bot_users.username`
  (нижний регистр), чтобы «Песочница» находила людей по @username.
- Валюты (`app/currency.py`): курс 1🍬 = 0,8 ₽ = 0,01 $. В «Песочнице» сумму можно вводить в 🍬, ₽ или $; за ₽/$ пользователь
  получает «Вы купили N🍬 за X₽/$», за 🍬 — «Вы получили +N🍬». Расчёты только на Decimal, конфеты округляются половина вверх.
- Баланс 🍬 живёт только в БД (`bot_users.candies`). Менять его — через `repo.add_candies` (атомарно, ниже нуля не уходит).
  Читать баланс для сообщений — `repo.get_candies` (запрос по ключу).

## Песочница (`app/sandbox.py`, вкладка на сайте)
Действует на текущего основного бота и только пока он запущен. Все разрушающие действия переспрашиваются в интерфейсе,
а API дополнительно требует `confirm: true`.
Действия: выдача/изъятие 🍬, «Удалить пользователя из базы», «Удалить все видео» («Удаляет все видео в галерее бота»,
`POST /api/sandbox/delete-videos`, `sandbox.delete_all_videos`) и «Уникальные текста». «Удалить все видео» стирает одобренные заявки
текущего бота (`repo.delete_gallery_videos`; ожидающие решения заявки не трогает) и сбрасывает кэш `video_pool`.

## Галерея бота: сколько видео и обнуление при смене бота
«Видео в галерее» = одобренные заявки бота (`repo.count_gallery_videos`). Число показано на вкладке «Бот» под пользователями и
временем жизни (`current.videos` в `/api/state`) и обновляется по SSE-событию `gallery` (при принятии видео модератором и после
«Удалить все видео»). Галерея принадлежит тому боту, который работал последним (`kv_settings.gallery_owner_bot`). При запуске
ДРУГОГО бота (`repo.reset_gallery_on_switch`, вызывается из `manager._run_bot`) все одобренные видео удаляются и галерея начинается с нуля
(так же при возврате к прежнему боту). Перезапуск того же бота (правка профиля, перезапуск приложения) галерею не трогает; самый первый
запуск после обновления только запоминает бота и ничего не удаляет.

## Пользователь заблокировал бота
Если пользователь сам заблокировал бота, он удаляется из БД вместе с балансом (`handlers.forget_user`: `stats.remove` + `flush`),
при следующем /start пройдёт капчу заново. Признаки (только они считаются «сам заблокировал»): событие `my_chat_member` со статусом
`kicked` в личном чате (`on_blocked_by_user`) и `TelegramForbiddenError` с текстом «bot was blocked by the user» при отправке
(`messaging.is_blocked_by_user`; в «Песочнице» при выдаче конфет — тоже). Другие 403 («user is deactivated», «can't initiate
conversation» и т. п.) пользователя НЕ удаляют.

## Картинка в уведомлениях
Короткие уведомления — «Вы получили +N🍬» / «Вы купили …» из «Песочницы», ответы предложки («❌ …» и «✅ Ваше видео принято на
рассмотрение.») — шлются БЕЗ картинки бота (`messaging.send_message(bot, chat_id, text)` без `image_url`). Картинка остаётся над приветствием,
галереей и меню предложки.

## Кнопки «Магазин» и «Галерея»
Отдельного главного меню нет: приветствие и есть меню, кнопки крепятся под ним (`handlers.send_greeting` ->
`messaging.send_message(..., reply_markup=shop_buttons.build_keyboard(texts.shop_buttons))`). Вид `shop_buttons` зарегистрирован
в `texts.KINDS` и живёт в `texts_config`, поэтому подписи, эмодзи, порядок, раскладка (один ряд / два ряда) и `callback_data`
(`sh:<хэш>` / `gl:<хэш>`, уникальны у каждого бота) не меняются при перезапусках, обновлениях кода и повторных `/start`; меняются
только кнопкой «Перенаписать текста». Текст и эмодзи выбираются независимо из отдельных списков в `app/shop_buttons.py`.
Нажатия разбирает `handlers.on_shop_button` через `shop_buttons.parse_action` (сверка с сохранённым ключом этого бота);
логика магазина и галереи там пока TODO.

## Цветные кнопки под сообщениями бота (ФАКТ: такая функция существует)
Telegram умеет красить inline- и reply-кнопки: поле `style` у кнопки (Bot API 9.4, февраль 2026). Допустимые значения:
`primary` — синяя, `success` — зелёная, `danger` — красная; без поля — обычная серая/прозрачная. Работает только в клиентах
Telegram, вышедших после 9 февраля 2026 (в старых кнопки показываются без цвета). Произвольные цвета (HEX и т.п.) задать нельзя.
В MTProto это флаги `bg_primary` / `bg_success` / `bg_danger`. Дополнительно можно поставить `icon_custom_emoji_id` (кастомный
эмодзи перед текстом; только если у владельца бота есть Telegram Premium или у бота куплены юзернеймы на Fragment).
В aiogram поле `style` есть с версии 3.25.0 (поэтому в `requirements.txt` стоит `aiogram>=3.25,<4`):
`InlineKeyboardButton(text=..., callback_data=..., style="primary")`.

Что сделано в проекте (решение владельца):
- под приветствием обе кнопки («Магазин» и «Галерея») синие — `shop_buttons.BUTTON_STYLE = "primary"`;
- в галерее по порядку: покупка видео — синяя, премиум — зелёная, «Предложка» — синяя, «Назад» — красная — `gallery.ROW_STYLES`;
- капча без цвета (владелец её не просил).
Цвет не рандомизируется и не хранится в БД — это константы в коде. Новые inline-кнопки красить только по просьбе владельца.

## Раздел «Галерея» и общий маркер
Нажатие «Галерея» под приветствием: приветствие удаляется, приходит сообщение галереи (`handlers.on_shop_button` -> `send_gallery`).
«⬅️ Назад» в галерее (фиксированный текст): сообщение галереи удаляется, приветствие отправляется заново (`on_gallery_button`).
Текст: `<b>подпись кнопки галереи этого бота</b>` (`shop_buttons.gallery_heading` — с теми же эмодзи, что на кнопке), описание в маркере, строка баланса —
последняя строка шаблона приветствия бота (`gallery.balance_line`), баланс из БД. Кнопки: покупка видео (цена 3🍬 в тексте, `gallery.PRICE`),
премиум, «Назад» — по одной в ряд; тексты и эмодзи выбираются независимо, `callback_data` (`gb:`/`gp:`/`gk:` + хэш) уникальны для бота.
Виды `gallery` и `deco` зарегистрированы в `texts.KINDS` (хранятся в `texts_config`, меняются только «Перенаписать текста»).
Маркер `texts.deco` — единая пара эмодзи для обрамления описаний: в новых разделах оформлять описание через `texts.deco.wrap(...)`.
Покупка видео реализована (см. раздел «Предложка» ниже), премиум — TODO в `handlers.on_gallery_button`. `last_gallery` (в памяти) не даёт галерее висеть рядом с приветствием после /start.

## Правила оформления кнопок и приветствия (актуально)
- Эмодзи на кнопках «Магазин» / «Галерея» / «Премиум» / «Купить» — только парой слева и справа (одиночных нет; исключение — «⬅️ Назад»).
- «Магазин» всегда стоит перед «Галереей». Заголовок раздела «Галерея» = подпись кнопки галереи (с её эмодзи).
- В приветствии между двумя пунктами нет пустой строки (вариант «airy» убран).
- Уже сохранённые в БД конфиги приводятся к этим правилам при чтении (`shop_buttons._migrate_legacy`, `greeting._tighten_points`, `gallery._LEGACY_PREMIUM`), без перезаписи БД.

## Предложка, модераторы и покупка видео (`app/suggest.py`, `moderation.py`, `video_pool.py`)
Пользователи шлют видео в «📩 Предложка 🤍» (кнопка в галерее перед «⬅️ Назад»), модераторы принимают их в боте, принятые видео
попадают в пул кнопки «Купить видео». Подпись кнопки «Предложка» и текст меню предложки **рандомизируются** (см. ниже, `suggest_ui.py`); остальные тексты
(ответы на видео, подписи заявок, кнопки модераторов) фиксированные. `callback_data` кнопки «Предложка» уникальны для бота.

**Меню и приём.** «Предложка» заменяет меню галереи (`handlers.send_suggest_menu`); «Назад» в нём возвращает меню галереи. Пока меню
открыто (`suggest_menu` в памяти, сбрасывается «Назад» и `/start`, после перезапуска бота — тоже), любое сообщение пользователя идёт в
`suggest.check`: не видео (в т. ч. текст, GIF, кружок, файл) / короче 30 с / длиннее 3600 с — ответ с причиной; 30 и 3600 проходят.
**Кулдауна нет** — видео можно слать подряд. Автор из `blocked_authors` игнорируется молча (заявка не создаётся, ответа нет).
Подходящее видео получает ответ «✅ Ваше видео принято на рассмотрение.» (`suggest.MSG_ACCEPTED`). Файлы не скачиваются: в `video_submissions` хранятся `file_id`,
`file_unique_id`, длительность, автор, статус `pending/approved/rejected`, `decision` (`approve/reject/block/block_auto`) и кто решил.
`file_id` действует только у бота, получившего видео, поэтому заявки и пул привязаны к `bot_id` (как баланс 🍬): после ротации токена
у нового бота пул одобренных видео начинается заново. Модераторы и чёрный список авторов — общие для всех ботов.

**Модераторы** (`moderators`, вкладка «Модераторы» на сайте, API `POST /api/moderators`, `DELETE /api/moderators/{id}`). Добавляются по
`@username` или ID; пользователя может не быть в `bot_users`. Запись по юзернейму получает `user_id` при первом обращении к боту
(`moderation.cache.touch` — на каждое сообщение и callback, кэш 30 с; если человек уже есть в `bot_users`, ID подставляется сразу).
Права модератора — только кнопки заявок в боте, к сайту доступа нет (на сайте один пароль администратора). Писать можно только тем,
у кого известен ID и кто запускал бота (`TelegramForbiddenError` при рассылке молча пропускается).

**Рассылка и решения.** `moderation.deliver`: видео каждому модератору с `protect_content=True` и тремя кнопками (`mod:a|r|b:<id>`,
не цветные), `chat_id`/`message_id` пишутся в `submission_messages`. Решение — `repo.decide_submission`: один
`UPDATE ... WHERE status='pending'` в транзакции с начислением, поэтому при одновременных нажатиях выигрывает один, +2🍬 не
дублируются (`suggest.REWARD`); второй получает «Заявка уже обработана». После решения `moderation.sync_messages` у ВСЕХ
модераторов убирает кнопки и дописывает «принята / отклонена / автор заблокирован модератором @username» (нет юзернейма — имя и ID).
«Заблокировать»: автор в `blocked_authors`, его остальные `pending`-заявки закрываются как `block_auto` (сообщения у модераторов тоже
обновляются). Отклонение и блокировка конфет не дают.

**Покупка** (`handlers.buy_video`, 3🍬 = `gallery.PRICE`). Списание — атомарный `repo.spend_candies` (`candies >= 3`, один UPDATE)
ДО отправки; не хватило — alert «❌ У вас недостаточно средств»; успех — без всплывающих окон. Видео — случайное из `video_pool`
(пул кэшируется в памяти с `file_id`, пополняется при принятии заявки; недавно показанные пользователю не повторяются, пока есть
другие). Нельзя отправить (устаревший `file_id`) — видео на 10 минут исключается и берётся другое (до 3 попыток); не вышло совсем или
пул пуст — конфеты возвращаются. Видео: без подписи, `protect_content=True`, ровно две кнопки (та же покупка и «⬅️ Назад»; цвета как в галерее).
Купленные видео не отслеживаются и никогда не удаляются. «Назад» под видео: видео остаётся, tracked-меню галереи (`last_gallery`) удаляется,
приходит новое меню галереи; «Назад» в самом меню галереи по-прежнему удаляет его и шлёт приветствие; `/start` удаляет меню галереи.
Баланс в уже висящем меню галереи после покупки не обновляется (новое меню покажет актуальный).

## Статистика в подвале сайта (`app/metrics.py`)
Блок «Статистика за всё время» внизу панели (под всеми вкладками): трафик, операции БД, HTTP-запросы, события предложки и выдачи.
- Счётчики только в памяти (`metrics.add`), в БД уходят **дельтой** раз в 45 с (`Metrics.run`) и при штатной остановке (`lifespan` в
  `main.py`): `repo.add_metrics` под блокировкой строки прибавляет дельту к JSON в `kv_settings["metrics_totals"]`, поэтому два
  одновременно работающих процесса (деплой) не затирают друг друга. Нет изменений — нет записи в БД. При старте итоги подтягиваются (`metrics.load`).
- Трафик и HTTP-запросы: ASGI-middleware `MetricsMiddleware` (тела + заголовки; без TLS/TCP-накладных и без трафика Telegram).
  Опрос `/api/metrics` и само сохранение в счётчики не попадают. Операции БД: событие SQLAlchemy `after_cursor_execute` (`db.init_db`).
  События: `submissions` (создана заявка), `decisions` (решение модератора), `videos_sent` (видео выдано при покупке).
- Страница опрашивает `GET /api/metrics` раз в 3 с (пока вкладка видна); эндпоинт читает только память, в БД не ходит.
- Это счётчики уровня приложения, а не биллинг Render/БД — в подвале об этом честно сказано. Новые поля добавлять в `metrics.FIELDS`.

## «Предложка»: рандомизация кнопки и меню (`app/suggest_ui.py`)
Вид `suggest` (в `texts.KINDS`, хранится в `texts_config`, меняется только «Перенаписать текста», у бота создаётся один раз по токену).
Кнопка в галерее: `{левый эмодзи} {название} {правый эмодзи}`; название (5 вариантов), левый (4) и правый (7) эмодзи выбираются независимо.
Меню предложки: заголовок = та же подпись, ниже одно из 5 синонимичных описаний с «+2🍬 за каждое принятое видео», обрамлённое одним из 6
декоративных эмодзи (с обеих сторон; общий маркер `deco` меню предложки больше не использует). Эталон `gallery.SUGGEST_LABEL` остаётся только
значением по умолчанию в `gallery.layout_rows` / `build_keyboard` — в боте подпись берётся из `texts.suggest.label`. У уже работающих ботов
вид `suggest` создаётся при ближайшем запуске (остальные их тексты не меняются), поэтому их кнопка «Предложка» после обновления получит свой вариант.

## Подсказка «как заработать конфеты» в галерее
Сообщение галереи: заголовок, описание в маркере, **подсказка**, баланс — через пустую строку (`gallery.render`). Подсказка — один из 4
шаблонов `gallery.HINTS` с `{proposal_title}`; шаблон выбирается по seed бота и хранится в конфиге галереи (`hint`, вид `gallery`).
`{proposal_title}` подставляется при отправке из `texts.suggest.name` — название кнопки предложки этого бота без эмодзи (берётся из
сохранённой подписи `suggest.label`), поэтому подсказка всегда совпадает с кнопкой на экране, в том числе после «Перенаписать текста».
Число конфет в подсказке не указывается (проверяется при загрузке таблиц). У конфигов без `hint` вариант выводится из `back_cb`
(`GalleryConfig.hint_template`) — стабильно, без перезаписи БД. Уже висящее в чате сообщение галереи не обновляется, новое покажет актуальный текст.
