# Заметки для разработки (читать перед правками сообщений бота)

## Рандомизация сообщений бота — ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ПРОЕКТА

В проекте есть структура рандомизации сообщений: у каждого бота свой, один раз подобранный и затем неизменный
вариант текста — случайные синонимы, близкие по смыслу эмодзи, несколько вариантов компоновки.

**Сейчас рандомизированы:** капча (`app/captcha.py`) и приветствие (`app/greeting.py`).

**В будущем это будет добавляться к другим сообщениям бота.** Если владелец проекта просит для нового сообщения
«рандомизацию», «как у приветствия/капчи», «подбор синонимов и смайликов» — делайте по схеме ниже, не изобретая
новую. Если он просит новое сообщение бота без таких оговорок — спросите, нужна ли рандомизация.

### Правила (общие для всех сообщений)
1. Вариант создаётся **один раз при создании бота** (при первом запуске) детерминированно по seed = токен бота
   и хранится в БД. Перезапуски, обновления кода, повторные `/start` его не меняют.
2. Хранить нужно **готовый результат** (для текста — шаблон с плейсхолдерами вроде `{name}`, `{balance}`),
   а не только индексы: правки словарей в коде не должны менять тексты уже работающих ботов.
3. Новый вариант у разных ботов не должен совпадать (`signature()` + набор `taken`).
4. Единственный способ сменить вариант у живого бота — кнопка «Перерандомизировать» во вкладке «Песочница»
   (меняет сразу все виды сообщений, применяется без перезапуска бота, с переспросом).
5. Смысл не меняется: синонимы равнозначны, тон нейтральный и спокойный (без фамильярности).
6. Эмодзи подбираются наборами (палитрами), которые сочетаются по стилю. Нельзя менять 🍬 — это валюта бота.
7. Никаких декоративных разделителей (`———`, `---`, `***`) и псевдографических рамок.
8. Индексы в словарях синонимов/эмодзи только **добавляются в конец**, не переставляются и не удаляются.

### Как добавить новое рандомизируемое сообщение
1. Создать модуль `app/<имя>.py` по образцу `app/greeting.py`: словари синонимов и эмодзи, `generate_config(seed, taken)`,
   конфиг-класс с `to_json()`, `from_json()`, `signature()`, функция `render(...)`.
2. Зарегистрировать в `app/texts.py`: добавить `TextKind(...)` в `KINDS` и свойство в `BotTexts`.
   Хранение отдельной колонки не требует: всё новое лежит в `bot_profiles.texts_config` (JSON `{вид: JSON-конфиг}`).
   (Капча исторически лежит в `bot_profiles.captcha_config` — `LEGACY_COLUMNS`.)
3. Больше ничего подключать не надо: `repo.get_or_create_texts` создаст вариант при запуске бота, а кнопка в «Песочнице»
   перерандомизирует его вместе с остальными. Отправку сообщения в `handlers.py` делать через `texts.<вид>`
   (читать в момент отправки, не кэшировать), чтобы перерандомизация действовала без перезапуска.
4. Добавить пример и проверки в `tests/` (детерминированность, сохранение 🍬, отсутствие разделителей).
5. Если у сообщения есть динамические значения (имя, число) — подставлять их в момент отправки, экранируя HTML.

## Пользователи и конфеты
- Пользователь считается «новым» и попадает в БД **только после успешной капчи** (`UserStats.add` вызывается лишь из
  обработчика верного ответа). Не прошедшие капчу не пишутся в БД вообще.
- Проверка «прошёл ли капчу» — по словарю в памяти (`UserStats`), записи в БД копятся и уходят одной транзакцией
  на пачку (`flush`, раз в 15 с и сразу после прохождения капчи). Юзернейм пользователя хранится в `bot_users.username`
  (нижний регистр), чтобы «Песочница» находила людей по @username.
- Баланс 🍬 живёт только в БД (`bot_users.candies`). Менять его — через `repo.add_candies` (атомарно, ниже нуля не уходит).
  Читать баланс для сообщений — `repo.get_candies` (запрос по ключу).

## Песочница (`app/sandbox.py`, вкладка на сайте)
Действует на текущего основного бота и только пока он запущен. Все разрушающие действия переспрашиваются в интерфейсе,
а API дополнительно требует `confirm: true`.
